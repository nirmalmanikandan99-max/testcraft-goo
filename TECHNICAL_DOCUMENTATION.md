# TestCraft Goo — Technical Documentation

This document describes the architecture, data flow, security model and deployment details of **TestCraft Goo**, an AI-powered manual test-case generator.

---

## 1. Overview

TestCraft Goo is a **single-module Streamlit application** that turns a functional document plus a user story into structured, downloadable test cases. It uses an LLM in a 4-stage pipeline and supports **four AI backends** (one local, three online), per-user API keys, and either local (SQLite) or cloud (Neon Postgres) user storage.

```
┌────────────┐   ┌─────────────┐   ┌──────────────┐   ┌─────────────┐
│ Requirement│   │  Technique  │   │  Test-Case   │   │   Excel     │
│  Analysis  │──▶│  Selection  │──▶│ Generation   │──▶│   Export    │
└────────────┘   └─────────────┘   └──────────────┘   └─────────────┘
      │                │                 │
      └────────────────┴─────────────────┘
                     │
              Unified LLM layer (src/llm.py)
      ┌──────────┬──────────┬──────────┬────────────┐
      │  Ollama  │  Gemini  │   Groq   │ OpenRouter │
      └──────────┴──────────┴──────────┴────────────┘
```

## 4. Pipeline Data Flow

1. **Input assembly** (`app.py`): document text + supporting docs + user story + format are combined into one `complete_context`.
2. **Stage 1 — `requirement_analyzer.analyze_requirements(context, llm_config)`**
   Calls the LLM with `requirement_analysis_prompt.txt`; expects JSON:
   ```json
   { "module_name": "", "summary": "", "input_fields": [], "business_rules": [],
     "validations": [], "workflow": [], "acceptance_criteria": [] }
   ```
3. **Stage 2 — `technique_selector.select_techniques(requirement_json, llm_config)`**
   Returns a JSON object of enabled testing techniques (`true/false`).
4. **Stage 3 — test-case generation, per technique (batched)**
   - The enabled techniques (truthy entries of the Stage-2 object) are taken in order and capped at `MAX_TECHNIQUES_PER_RUN` (8).
   - They are grouped into **batches of `TECHNIQUES_PER_BATCH` (2)**; each batch is generated by one call to
     `testcase_generator.generate_testcases_for_techniques(requirement_json, [techniques], format, llm_config)`.
   - The prompt embeds a **pre-filled JSON skeleton**: `MIN_CASES_PER_TECHNIQUE` (4) numbered rows per technique, each row already carrying its `Testing Technique` tag. The model must fill every row — this reliably produces the full count (free-tier reasoning models otherwise collapse to 1 row).
   - **Top-up retry:** if a reply parses to fewer rows than expected, one follow-up call demands the missing distinct rows; results are de-duplicated by title.
   - Rows are bucketed back to techniques by `group_rows_by_technique()` (case-insensitive tag match; unknown tags fall back to the least-populated technique), then flattened and renumbered by `merge_technique_testcases()` (stamps `Testing Technique`, sequential `S.No`).
   - If `technique_json` has no enabled techniques, the pipeline falls back to the single-batch `generate_testcases()`.
   - 6s pacing between batches; a failed/slow batch raises `LLMError` → the UI shows a warning and **skips the batch** so the run still completes and exports Excel.
5. **JSON safety — `json_validator.validate_json(raw)`**: strips ```json fences, tries `json.loads`, then falls back to extracting the outermost `[...]` or `{...}` block.
6. **Stage 4 — `excel_generator.generate_excel(test_cases, path, format)`**: writes a styled workbook (header fill, borders, freeze pane, auto-filter, column widths) with either the Conventional or GWT column layout.
7. Results are cached in `st.session_state["results"]` so they survive reruns (e.g. download clicks). A **generation log** (see §5.5) is available for download alongside the Excel file.

Every stage accepts an optional `llm_config` so the selected engine flows through the whole pipeline.

### Pipeline tuning constants (`src/config.py`)

| Constant | Value | Purpose |
|---|---|---|
| `JSON_RETRIES` | `3` | Parse-failure retries per stage (failed output is fed back as a correction hint) |
| `MAX_TECHNIQUES_PER_RUN` | `8` | Cap on techniques processed in one run |
| `MIN_CASES_PER_TECHNIQUE` | `4` | Skeleton rows per technique; also the top-up target |
| `TECHNIQUES_PER_BATCH` | `2` | Techniques per Stage-3 call (smaller calls are faster than big ones) |
| `ANALYSIS_TEMPERATURE` | `0.1` | Deterministic analysis/selection |
| `GENERATION_TEMPERATURE` | `0.2` | Slightly varied test cases |
| `ANALYSIS_NUM_PREDICT` / `GENERATION_NUM_PREDICT` | `16384` / `16384` | Token budget; generous because Gemini 3.x *thinking tokens count against max_tokens* (budgets of 300–1024 caused truncated JSON; 16384 verified stable) |
| `SYSTEM_JSON_RULE` | system prompt | Forces a single JSON object/array — prepended to stages 1–2 |
| `SYSTEM_ARRAY_RULE` | system prompt | Forces a JSON **array** of test-case rows — prepended to Stage 3 |

## 5. LLM Provider Layer (`src/llm.py`)

### 5.1 `LLMConfig`

```python
LLMConfig(provider="ollama" | "gemini" | "groq" | "openrouter", api_key="", model="")
```

`effective_model()` resolves defaults per provider:

| Provider | Default model | Base URL (OpenAI-compatible) | Fallback chain |
|---|---|---|---|
| `ollama` | `qwen2.5:7b` | (local) | — |
| `gemini` | `gemini-3-flash` | `https://generativelanguage.googleapis.com/v1beta/openai` | `gemini-3.5-flash`, `gemini-3-flash`, `gemini-flash-latest`, `gemini-2.5-flash`, `gemini-2.5-flash-lite`, `gemini-3.1-flash-lite` |
| `groq` | `llama-3.3-70b-versatile` | `https://api.groq.com/openai/v1` | `llama-3.3-70b-versatile`, `llama-4-scout`, `qwen3-32b` |
| `openrouter` | `google/gemma-4-26b-a4b-it:free` | `https://openrouter.ai/api/v1` | `openai/gpt-oss-20b:free`, `google/gemma-4-31b-it:free`, `nvidia/nemotron-3-ultra-550b-a55b:free`, `nvidia/nemotron-3-super-120b-a12b:free` |

The OpenRouter order is a **live benchmark ranking** (gemma-4-26b-a4b-it answered 8 rows in 52s; gpt-oss-20b took 152s; the Nemotron reasoning models burn their output budget "thinking" and return 1 row — they are demoted to last resort).

### 5.2 `chat(config, prompt, temperature, num_predict, system=None, json_mode=False) -> str`

- **ollama**: lazy `from ollama import chat`; options `{temperature, num_predict}`.
- **gemini / groq / openrouter**: POST to `{base}/chat/completions` with
  `Authorization: Bearer <api_key>` and body `{model, messages, temperature, max_tokens}`;
  `json_mode=True` adds `response_format={"type": "json_object"}` (all three online
  providers support it). On a `400` from json mode, the call is retried without it.

### 5.3 Resilience (automatic)

| Condition | Behaviour |
|---|---|
| `404` unknown model | Retried against the provider's **fallback chain** (`_model_candidates`) |
| `429` rate limit | Backoff (5s/20s/45s, honors `Retry-After`, capped 60s) on the first limited model — free-tier quotas are **per model**, so subsequent candidates each get one shot with a 3s gap, rotating through every fallback. Exhausted → friendly error (per-minute vs daily limit) |
| `400` on json_mode | Retried on the same model without `response_format` |
| `401` bad key | Friendly error naming the provider |
| `402` (OpenRouter) | Friendly "add credits or use `:free` models" error |
| `5xx` / error-in-body | One retry after 10s, then "temporarily overloaded" |
| Slow upstream | `CALL_TIME_BUDGET = 180s` total wall-clock per call (the httpx read timeout is per socket-read, so a trickling upstream could otherwise hang a batch for many minutes) — raises a clear "congested" error |
| Connect failure | Friendly "check your internet connection" error |
| Unexpected shape | Raw response preview in the error |

### 5.4 `test_connection(config) -> (bool, str)`

Sends a tiny `"Reply with the single word: OK"` probe. Never raises.

### 5.5 Usage log & generation log

- `_record_usage(provider, model, headers, usage)` collects one event per successful call: model, prompt/completion/total tokens, and provider rate-limit headers. `clear_usage_log()` / `usage_log()` expose it.
- `app.py` snapshots the log between stages and builds a downloadable **Generation Log** (`_build_generation_log`) with per-stage: model used, tokens in/out/total, and rate-limit headers (or "not reported").
- `fetch_provider_limits(config)` queries OpenRouter `GET /auth/key` for account-level usage (free tier status, credits used, daily usage) — included in the log; returns `None` for providers that don't expose it.

> Keys are held only in memory (session state / DB decrypt-on-read) — never logged.

## 6. Authentication & Data Persistence (`src/auth.py`)

### Database abstraction
Selected at **module import time** from `DATABASE_URL`:
- Starts with `postgres` → `psycopg` (v3) with `dict_row` row factory.
- Otherwise → `sqlite3` with `Row` factory and `AUTH_DB_PATH` override (used by tests).

SQL placeholders are resolved per-dialect via `_placeholder()` (`?` vs `%s`).
`init_db()` runs DDL in **autocommit** mode — important on Postgres, where a failed
`ALTER TABLE` (e.g. column already exists) would otherwise abort the transaction and
roll back the `CREATE TABLE`.

### Schema (`users`)
| Column | Type | Notes |
|---|---|---|
| id | PK | `AUTOINCREMENT` (SQLite) / `SERIAL` (Postgres) |
| first_name / last_name / email / phone | TEXT | email & phone UNIQUE |
| password_hash / salt | TEXT | PBKDF2-HMAC-SHA256, 200k iterations |
| created_at | TEXT | ISO timestamp |
| api_provider | TEXT | `'gemini'` (default) / `'groq'` / `'openrouter'` |
| api_model | TEXT | user-selected model (overrides the config default) |
| api_key_encrypted | TEXT | Fernet ciphertext ('' if none) |

### Security
- **Passwords**: salted PBKDF2-HMAC-SHA256 (`hashlib`), constant-time compare.
- **API keys**: encrypted with **Fernet**. The master key is resolved from
  `ENCRYPTION_KEY` (env / Streamlit secret); locally, a git-ignored `.encryption_key`
  file is auto-generated on first use.
- **Encryption round-trip** is covered by `tests/test_auth.py` (ciphertext never
  contains the plaintext key).

### Key management API
- `create_user(..., api_provider, api_model, api_key)` — optional key at signup
- `update_api_key(user_id, provider, model, api_key)` / `clear_api_key(user_id)`
- `get_api_key(user_id)` — decrypts on demand (returns `''` if none)
- `get_user_by_id(user_id)` — refreshed public profile after key edits
- `authenticate_user(identifier, password)` — login by email **or** phone

## 8. Deployment

### A. Local development
```powershell
python -m venv venv; venv\Scripts\activate
pip install -r requirements.txt
venv\Scripts\python -m streamlit run app.py
```
SQLite fallback is automatic when `DATABASE_URL` is absent. `.streamlit/secrets.toml`
and `.encryption_key` are git-ignored.

### B. Streamlit Community Cloud (free)
1. Public GitHub repo, branch `main`, main file `app.py`.
2. Secrets: `DATABASE_URL` + `ENCRYPTION_KEY`.
3. Auto-redeploys on every push. If the app page shows `ImportError: cannot import name ...` right after a push, the process is running a stale in-memory module — use **Manage app → Reboot** (or push again) for a clean restart.

### C. Desktop EXE (offline)
`launcher.py` switches to the frozen dir, opens the browser, and runs
`streamlit run app.py` headless. Requires local Ollama with the model pulled.

## 10. Known Constraints & Free-Tier Limits

| Area | Limit |
|---|---|
| Gemini free tier | ~10 req/min, ~1,500 req/day per model, ~250K tokens/min |
| Groq free tier | Generous token rates; regional availability varies |
| OpenRouter `:free` | ~20 req/min, **50 req/day** (1,000/day after a one-time $10 top-up); request-based, no token quota; no rate-limit headers (usage via `/auth/key`) |
| Streamlit Cloud | Ephemeral disk (use Neon for persistence); hosting badge (outside app iframe, auto-fades ~5s) |
| Prompt/context | No chunking yet — very large PDFs can exceed context; consider RAG/chunking |
| Techniques | Catalog defined in `technique_selector_prompt.txt`; capped at 8 per run |
| Output | Single-sheet Excel; no editable pre-export review, no traceability matrix |
| Stage-3 count | `4` cases per technique guaranteed via skeleton + top-up; more only if the model over-fills |
